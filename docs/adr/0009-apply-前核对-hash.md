# 0009 Apply 前核对文件 hash，被外部改过就拒绝

- 状态：已接受
- 日期：2026-11-02

## 背景

一次运行可能持续几分钟，期间用户可能在 Obsidian 中编辑 Vault。Staging 是基于运行开始后读到的内容计算出来的，如果直接写盘，会静默覆盖用户的编辑。

## 决策

1. **记录 Base**：运行中第一次读取或写入某个文件时，记录它在 Vault 中的内容 hash（文件当时不存在也要记录为“不存在”）。
2. **Apply 前核对**：
   - Proposal 中要写的文件，当前 hash 与 Base 不一致（包括本来不存在、现在被创建了）→ 拒绝整个 Apply，列出发生变化的文件。用户可以选择重新运行。
   - 只读过、没写过的文件发生变化 → 不拒绝，但会触发下一步的重新校验。
3. **重新校验**：基于“当前 Vault + Staging”重新运行全部 Invariant（例如被链接的页面可能已被删除）。不通过就拒绝 Apply。
4. **写入**：每个文件先写临时文件，再 rename 覆盖。不做跨文件事务；万一中途失败，依赖 Vault 自身的 git 恢复，并在输出中列出已写入和未写入的文件。

## 不做

- 三方合并。
- 跨文件的原子提交或自动回滚。

## 影响

- 运行期间编辑了 Proposal 涉及的文件，这次运行的结果就作废，需要重跑。
- v1 不阻止对同一个 Vault 同时发起多个 Run。后 Apply 的那个会因为 hash 不一致被拒绝，不会出现静默覆盖。
- Apply 依赖 Vault 是 git 仓库来兜底；Vault 不是 git 仓库时，Apply 前要给出警告。
