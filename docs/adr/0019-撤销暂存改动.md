# 0019 Agent 可以撤销单个文件的暂存改动

- 状态：已接受
- 日期：2026-11-03
- 修订：0005 中“v1 不提供删除和移动”；0010 的工具表；0014 中 `staging/write` 的操作类型

## 背景

M6 用 flash 对 S1 补跑了一次 Revise（Run `2026-11-03T05-43-24Z-c5098378`）。第一份 Proposal 新建了 6 页，修改意见要求把其中 3 页并入另外 2 页。模型合并了内容，却没法把这 3 个本次新建的文件从 Staging 中去掉，只能留下 3 个一行的跳转页，并在 `log.md` 里写明“因工具无删除能力……确认时可手动删除”。它第一次把这 3 页写成空壳时触发了 6 条 Warning（frontmatter 字段、出链数），随后给跳转页补齐 frontmatter 和链接，Warning 就消失了。

0005 的“不提供删除”是为了让 Apply 不删除 Vault 中的文件，但 Staging 也没有撤销手段，于是 Agent 连自己本次新建的文件都收不回来。拆页过碎是 M6 验收中 flash 最主要的问题，而 Revise 是用户纠正它的唯一途径。

## 决策

新增工具 `revert_file(path)`：撤销本次 Run 对这个文件的全部暂存改动，让它回到 Vault 中的状态。

- 本次新建的文件：从叠加视图和 Proposal 中消失。
- 修改过的已有文件：恢复为 Vault 中的内容，不再出现在 Proposal 中。
- 文件没有暂存改动时报错。
- 不检查 Write Scope：撤销的结果总是 Base，不会越界。
- Apply 仍然只写入、不删除。Vault 中已有的文件不能被任何工具删除或移动，0005 的这条限制不变。

撤销的后果由已有校验兜底：`index.md`、`log.md` 或其他页面中指向被撤销页面的新链接，会被链接 Invariant 拦下，Agent 必须一并改掉。

## 考虑过的方案

- **保持现状，Apply 后人工删除**：每次合并都会留下跳转页；Warning 还会促使模型把跳转页修饰成合格页面，人工清理容易遗漏。
- **`write_file` 写空内容表示删除**：语义隐式，空文件本身也是合法内容，无法区分。
- **真正的删除工具，包括 Vault 中已有的文件**：Apply 需要删除语义，Write Scope 需要删除规则，确认环节也要展示删除；v1 的 Ingest 用不到删除已有页面。

## 影响

- 0010 的工具表增加 `revert_file`；“没有删除、移动”仍然适用于 Vault 中已有的文件。
- Trajectory 的 `staging/write` 增加 `revert` 操作；撤销本次新建的文件时，写入后的 hash 为空。
- `result.json` 的 `files` 仍然列出写过的文件，包括后来被撤销的；最终改动以 `proposal/diff` 为准。
