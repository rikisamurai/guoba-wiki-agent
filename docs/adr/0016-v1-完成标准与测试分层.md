# 0016 v1 完成标准：三层测试

- 状态：已接受
- 日期：2026-11-02

## 背景

v1 的大部分复杂度在机制上：Finish 修正回路、Write Scope、上限、Apply 前的 hash 核对、Trajectory。这些分支用真实模型几乎无法稳定触发；而 Skill 的效果、DeepSeek 的协议兼容、真实费用，又只有真实模型才能验证。

## 决策

v1 必须同时满足以下三层。

### 1. faux 自动化测试（默认 CI，必须全部通过）

使用 pi-ai 内置的 `fauxProvider()` 按剧本返回模型响应，不需要 API Key。至少覆盖：

- Finish：一次通过；Invariant 失败后修正通过；连续 3 次失败后运行失败且不能 Apply；只有 Warning 时第二次 Finish 放行；模型不调用 Finish 就停止。
- `finish` 与其他工具出现在同一批调用中时被拦截。
- Write Scope：越界写入当场报错；`sources/**` 中除 `ingested-at` 以外的改动被拦截；`log.md` 非追加改动被拦截。
- 三个上限分别触发。
- provider 返回错误、用户取消。
- Apply：正常写入；运行期间目标文件被外部修改时拒绝；只读文件变化后重新校验。
- Revise：反馈进入同一 Staging，共用原运行的上限。
- Trajectory：事件 `seq` 连续，事件序列能还原出 Turn/Step 结构，`result.json` 可以由 Trajectory 重新生成。

用 faux 的工厂函数形式断言模型收到的上下文，例如校验反馈确实出现在下一次请求中。

查看器的投影逻辑用 Vitest 测，以真实格式的 Trajectory fixture 作为输入；关键交互用 Playwright 测。

### 2. 真模型冒烟测试（可选，不进默认 CI）

- 命令：`pnpm test:live`。只有设置了 `DEEPSEEK_API_KEY` 才运行，否则跳过。
- 用一份很小的 fixture Source 在临时 Vault 副本上跑一次 ingest。
- 只断言 Invariant 全部通过、Trajectory 完整、Usage 与费用被记录；不断言页面内容。

### 3. 真实 Source 人工验收

- 在 ai-wiki 的 git worktree（单独分支）上运行，Apply 只写入这个 worktree，不影响主分支。
- 选 3 份历史 Source：小、中各一份，以及最大的一份（约 5.9 万字符，`sources/clippings/你不知道的 Agent：原理、架构与工程实践.md`）。
- 通过条件：Invariant 全部通过；用户看过 diff、愿意 Apply；网页查看器能完整回放这 3 次 Run。

## 不做（留到 v2）

- 回放 85 次历史 ingest 做系统评测。
- `deepseek-flash` 与 `deepseek-v4-pro` 的对比（0011）。

## 影响

- fixture 需要从 ai-wiki 截取一个小型 Vault：若干 Wiki Page、`index.md`、`log.md`、几份 Source，以及 ingest Skill 的副本。ai-wiki 是公开仓库，fixture 可以随本仓库公开。
- 人工验收依赖用户本机的 ai-wiki 仓库和 DeepSeek API Key。
